# Отчёт по лабораторной работе №1

## Вариант и цель

Вариант №1871303: веб-приложение на Java/Spring Boot, предметная область «библиотека», основной объект «событие», пользовательская роль «менеджер», обязательный сценарий «оформление заказа». Цель — исследовать использование Etcd как key-value хранилища, включая leases, кэширование, атомарный счётчик и конкурирующие записи.

## Архитектура и представление данных

Приложение разделено на стандартные для Spring-проекта слои: `controller`, `dto`, `service`, `model`, `repository`, `exception` и `config`. Контроллеры принимают HTTP-запросы, специализированные сервисы реализуют сценарии, а `EtcdGateway` изолирует работу с Jetcd. Etcd разворачивается одним узлом через Podman Compose, данные узла размещаются в постоянном volume.

Ключ содержит тип и идентификатор сущности, а значение — JSON:

```text
/library/events/{eventId}       -> Event JSON
/library/orders/{orderId}       -> Order JSON
/library/drafts/{draftId}       -> DraftOrder JSON + lease
/library/settings/{managerId}   -> ManagerSettings JSON
/library/views/{eventId}        -> integer as UTF-8
```

Префиксы группируют однотипные объекты и позволяют получить их range-запросом. UUID обеспечивает равномерные уникальные ключи. JSON выбран из-за читаемости и удобной эволюции схемы; для счётчика выбран простой числовой текст, поскольку его требуется читать и заменять в CAS-цикле. Недостаток JSON — отсутствие серверной проверки схемы и невозможность изменить отдельное поле без перезаписи значения.

## Временная заявка и оформление заказа

Для временной заявки сервер выдаёт lease на 5–86400 секунд и выполняет `put` с идентификатором lease. По окончании TTL удаление происходит внутри Etcd, поэтому оно не зависит от работающего экземпляра Spring Boot.

При оформлении заказа приложение читает заявку вместе с `mod_revision`, затем выполняет транзакцию. Условия транзакции: событие существует, ревизия заявки не изменилась. Успешная ветка одновременно записывает постоянный заказ и удаляет заявку. Два менеджера не смогут оформить один draft: для одного транзакция завершится успешно, второй получит конфликт 409.

## Кэширование

Настройки менеджера читаются по cache-aside: сначала проверяется потокобезопасный локальный кэш, при промахе выполняется чтение Etcd и значение кэшируется на 60 секунд. Запись настройки сначала сохраняет её в Etcd, затем удаляет старую запись из кэша. Размер ограничен 1000 элементами; при достижении границы кэш очищается.

Такой кэш эффективен для одного экземпляра приложения. При горизонтальном масштабировании локальные кэши могут до 60 секунд видеть устаревшие значения. Для production-варианта следует инвалидировать их через Etcd Watch либо применять общий внешний кэш.

## Атомарный счётчик

Etcd не предоставляет отдельной команды `INCR`. Алгоритм читает значение и его `mod_revision`, вычисляет `n + 1`, затем транзакционно сравнивает текущую ревизию с прочитанной. При успехе записывается новое значение, при конфликте цикл повторяется. Благодаря линейризуемым операциям успешные увеличения не теряются.

CAS требует нескольких сетевых операций и под высокой нагрузкой создаёт конфликты. Поэтому Etcd подходит для умеренно изменяемых счётчиков метаданных, но для счётчика просмотров крупного публичного сервиса лучше использовать Redis, поток событий или пакетную агрегацию.

## Эксперимент параллельных записей

Endpoint `/api/experiments/write-conflict` запускает несколько потоков после общего барьера.

1. В режиме blind write каждый поток читает одно исходное значение, увеличивает его локально и выполняет безусловный `put`. Etcd сериализует записи, но не объединяет намерения клиентов: действует last-write-wins, и часть логических обновлений теряется.
2. В режиме CAS потоки сравнивают `mod_revision`. Только одна запись для каждой прочитанной ревизии проходит; остальные фиксируют конфликт, перечитывают значение и повторяют операцию. Конечное значение равно количеству участников.

Эксперимент показывает важное различие: линейризуемое хранилище гарантирует порядок отдельных операций, но read-modify-write становится атомарным только при использовании транзакции.

## Сохранение данных

Данные переживают перезапуск контейнера благодаря именованному volume `library-etcd-data`. Он подключён к каталогу `/etcd-data` внутри контейнера Etcd. Команда `podman compose down` останавливает контейнеры, но сохраняет volume; при следующем запуске ранее созданные записи остаются доступны.

Для переносимого сохранения скрипт `snapshot-save.sh` вызывает `etcdctl snapshot save` внутри работающего контейнера и копирует полученный файл на хост. Скрипт `snapshot-restore.sh` останавливает Compose, пересоздаёт только volume Etcd, выполняет `etcdutl snapshot restore` и запускает сервисы снова. Snapshot-файлы имеют расширение `.db` и исключены из репозитория.

## Вывод

Etcd применим для данной учебной системы и хорошо демонстрирует TTL через leases, оптимистичные транзакции, линейризуемое чтение и сохранение данных в volume. Он особенно уместен для настроек, координации, небольших заявок и данных, где важна строгая согласованность.

Ограничения заметны для библиотечного прикладного домена: нет вторичных индексов, полнотекстового поиска, связей и аналитических запросов; JSON-схема не контролируется хранилищем; большой поток счётчиков создаёт лишние CAS-конфликты. В реальной системе Etcd разумно оставить для конфигурации, временных координационных записей и блокировок, а события и заказы хранить в СУБД с индексами и транзакционной моделью предметной области.
